# AI Orchestrator 1.0.2: upgrade and testing guide

This release brings the accumulated Run diagnostics, cost-completeness and
memory-compaction recovery work into the Windows x64 portable package. Read the
[changelog](../../CHANGELOG.md) for the full list and the release's
`BUILD-VERIFICATION.txt` for the checks on the exact distributed build.

## Before updating

1. Close every AI Orchestrator instance.
2. Make a separate copy of the entire application-data folder, normally
   `%APPDATA%/AIOrchestrator/AIOrchestrator/`, including its database, artifacts,
   and proposal stores. Keep the old executable with that backup.
3. Download `AIOrchestrator-1.0.2-win-x64.zip` and its SHA-256 file from the
   [release](https://github.com/justVladislav/AI_Orchestrator/releases/tag/v1.0.2).
   Compare the digest using `Get-FileHash -Algorithm SHA256`.
4. Extract the entire archive into a new folder. Do not mix it with an older
   package or copy only the executable.
5. Start the new executable and check **Settings > Diagnostics** for version
   **1.0.2** and an available database.

The database moves to schema **75**. The published 1.0.1 package used schema 70;
intermediate source builds may have a different starting schema. Before an
existing database is upgraded, the application requires a verified SQLite online
backup in the profile's `backups` folder. That database copy is additional to
your own backup of the whole profile. Migration does not run if the required
backup cannot be made.

Do not reopen a migrated database with an older executable. A deliberate rollback
requires restoring the saved data and using its matching executable; copying the
old executable over the new folder is not a database rollback.

## Suggested first checks

### Existing data and a provider-free Run

- Check that your projects, Runs, chats, memory history and proposal records are
  still present. Do not Apply old proposals again merely to test the update.
- In a disposable project folder, use the Mock workflow with real providers
  disabled. Inspect the resulting stages, artifacts and diagnostics.
- Ordinary Mock tests do not prove a real provider call, project build, or GUI
  acceptance. Starting a real Run or compaction is a separate billable choice.

### Workspace boundaries and verification

- In a disposable project, inspect **Output folders** and use Preview before an
  explicit approval. The application does not infer approvals from `.gitignore`
  or CMake. Check the warning if sources are present under a proposed output
  folder before hiding that folder from context.
- New Manifest/context/follow-up work respects these approvals. Already-started
  work and Apply keep their recorded scope; revoking approval does not rewrite
  an older Run. These boundaries are not a sandbox for external build tools,
  and the execution-profile workflow does not yet consume these approvals.
- Project verification retains your presets and requires a confirmed Ninja/MSVC
  x64 configuration. A generator refusal is a setup diagnostic, not permission
  to rewrite the preset or assume a project build passed.
- Inspect Run Details for recorded exclusions and scope drift. A C++ exception
  can now reach normal Run finalization with diagnostics; abort/assert/SEH and
  every untested Unicode/path case are not claimed as handled.

### Costs and token history

- Overview's **Project cost estimate** includes recorded model executions and
  stored memory compactions, with their breakdown visible. **Recorded tokens**
  comes from the same project-cost result.
- A known amount, an incomplete estimate, an unknown price and an unavailable
  read are different states. A zero amount is not automatically proof that an
  operation was free. Unavailable reads clear stale totals and provider details.
- Chat totals use recorded attempts, including earlier attempts retained after
  clearing session counters. Comparison and memory history also show incomplete
  price information. Historical compaction amounts are not repriced with the
  current catalog.
- The built-in Sol price update applies only to the exact old seed. Custom
  pricing and already recorded historical amounts are preserved.
- Compare with your provider's own billing records when reconciling charges.
  The application shows recorded estimates, not an authoritative invoice.

### Memory compaction and recovery

- Compaction history can display reported usage and price completeness for
  Completed, Failed and Cancelled records. The operation result distinguishes
  saved accounting from an attempted record whose storage is unconfirmed.
- Unfinished-protocol coverage is separate from money. Counts describe records
  in the selected period, not an audit of every request or a live provider status.
  Open or unresolved does not establish whether a request was delivered or paid.
- A newly confirmed durable intent is required before dispatch. The owning file
  database's startup recovery inspects unfinished protocols without sending
  another provider request or creating a speculative cost row. The database
  recovery report is not limited to the currently selected project.
- A recovery/read error must remain visible independently of the last operation
  and other read errors. A coverage read can fail while a successful monetary
  read still shows its estimate.
- Do not crash the application or corrupt your live database to test recovery.
  Controlled process-crash cases use synthetic databases in the automated suite.

### Run diagnostics

- Missing provider-turn persistence is reported instead of remaining silent.
  Manifest/Profile reports keep diagnostic warnings without changing the
  original usage, acceptance verdict or failure reason.
- When automatic verification repair does not open a session, the report now
  explains the refusal. A missing session does not by itself mean that repair
  was disabled; capacity and diagnosis eligibility matter too.
- Structured OpenAI quota refusals have `provider.insufficient_quota`, separate
  from temporary rate limiting. Same-request transport retries are vetoed for
  these refusals; a configured fallback provider remains a separate policy.

## Known limits and verification scope

- An intermittent memory-history layout test failure remains under investigation.
  Passing runs have not established its cause or proved a permanent fix.
- Recovery handles process interruption. It does not establish provider delivery,
  billed cost after an interrupted call, or durability under power loss. Reads
  used for cost and coverage are separate best-effort observations, not one
  serializable snapshot.
- Truncated model output is not automatically continued by this release. Large
  single-worker tasks can still exhaust provider output/turn limits.
- The portable executable is unsigned. Windows x64/MSVC/CMake-presets remains the
  supported project-verification path; Comparison remains experimental.
- A successful automated suite does not imply a clean-machine GUI launch, a live
  API acceptance test, or verification of every existing project. Consult the
  release verification attachment rather than assuming those checks ran.

For clean-machine launch and optional upgrade testing, use the
[portable checklist](../../packaging/verify/CLEAN-MACHINE-CHECKLIST.md) inside a
clean Windows environment. Keep `-ExpectedSchema 75` explicit. To report a
problem, include the version, Run ID if applicable, exact code, reproduction
steps and redacted diagnostics. Never send credentials or an unreviewed profile.
